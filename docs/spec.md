# SMEAP 仕様メモ

SMEAP(Simple Markdown Editor for Astro Post)は、Astro製ブログ向けのシンプルなエディタ。MITライセンスで公開する。

## 決まったこと

### 対象と配布

- 対応OSはAndroid・Linux(Kubuntu)・Windows。LinuxとWindowsは実行ファイルを置いて使い、インストーラーは作らない
- Windowsの実行ファイルは署名しない(SmartScreenの警告が出る)。WebView2ランタイムが要る
- 配布用のビルドは`scripts/release-build.sh`(Linux・Windows)と`scripts/release-build-android.sh`で行う。ビルドした人の絶対パスを配布物に残さない

### 技術

- SCITLと同じTauri 2 + React + Vite + TypeScriptで作る。編集欄はCodeMirror 6
- SCITLの書き出し処理(Androidのzip)、トークン、アイコン、フォント、ビルド用スクリプトを流用する
- 外部との通信は、GitHubにログインしているときのRust側からGitHubへの通信だけにする([GitHub連携](#github連携))。画面は外と通信しない
  - CSPで通信先をアプリ内(Tauriのアプリ本体・IPC・ローカル画像の読み込み)に限る
  - フォントとアイコンはアプリに同梱し、CDNから読まない
  - 本文中の外部画像は読み込まず、生のHTMLは描画しない
  - Tauriの外部通信用プラグイン(httpなど)は入れない
- Rust側とTypeScript側の分担をはっきりさせる。画面側(TypeScript)は表示に必要な処理だけを行う
  - Rust側: 記事の一覧・作成・読み込み・保存、バックアップ、slugの検証と変更、フロントマターの組み立て、画像の取り込みと連番の採番、zipの書き出し、GitHubとの通信と認証
  - TypeScript側: 画面の表示、編集欄(CodeMirror)と装飾、入力の受け付け、保存するタイミングの判断(入力が止まったかどうかは画面側でしか分からないため)
  - slugの検証は、入力中の案内のために画面側でも行うが、最終的な判断はRust側で行う
- 画面の文言は`lang/{言語コード}.json`に置き、`t()`(`src/i18n.ts`)でキーから引く(Issue #41)
  - キーは`画面.要素`(複数の画面で使うものは`common.要素`)のドット区切りで入れ子にせず、キー順に並べる
  - 文を断片に分けてコードでつながない。1文を1キーにし、変わる部分は`{名前}`で差し込む
  - 文言は極力一言、多くても2文にする。「ません」は避ける。事実だけを書き、対処法は書かない
  - `t()`はモジュールの最上位で呼ばない(表示言語を起動時に決める形にしたとき、決まる前に引いてしまうため)。定数にはキーを持たせる
  - ログと例外の文は英語でコードに書く。画面に出るRustのエラー(`StoreError`・フロントマターの警告)は、言語を切り替えられるようにするときに扱う
  - `npm run lint`が、`src/`の文字列に日本語の直書きが残っていないかを確かめる

### 範囲

- 記事の読み書き・書き出しは1つの層(Rust側のコマンド)にまとめ、画面からファイルの場所を直接扱わない
- GitHubとの連携は[GitHub連携](#github連携)の節にまとめる(Issue #59)
- 編集できるのはこのアプリで作った記事だけ。外部の.mdは読み込まない
- Astroのプレビューは入れない。カスタムCSSも読み込まない
- ふつうのMarkdownのプレビューも置かない。編集欄で装飾のスタイルをその場で当てるので、書いた画面で仕上がりが分かる
- 画像の一覧の画面と名前の書き換えは作らない(Issue #15)。本文の画像は次の方法で`src/assets/{slug}/`にコピーし、本文に`![](...)`を入れる
  - 上のバーの画像のボタンからファイルを選ぶ(どのOSでも)
  - デスクトップ(Linux・Windows)ではクリップボードからの貼り付けとドラッグ&ドロップも受け付ける
- 画像のファイル名は記事ごとの連番(`01.png`など)にする
  - 挿入・貼り付け・ドロップのどれでも連番にそろえる
  - 番号は記事内の最大の番号+1(下の「使っていない画像」で移した画像の名前も数える)。消して空いた番号は詰めない
- 使っていない画像(Issue #15)
  - 保存のたびに、`assets/{slug}/`の直下の通常のファイル(拡張子は問わない)のうち、画像として表示される参照が無いものを、アプリのデータ領域の`backup/{記事のディレクトリのパスのハッシュ}/removed-images/{slug}/`へ移す。下のディレクトリ、シンボリックリンク、共有の画像は扱わない
  - 参照とみなすのは、本文の`![...](../../assets/{slug}/{名前})`とHTMLの`<img src="...">`、`[id]: パス`の定義(`![a][id]`の画像のため。リンクにだけ使う定義も含む)、heroImage、heroImage以外のフロントマターの項目に書いたパス(`ogImage`など)。リンク`[...](...)`や地の文に書いたパスは参照とみなさない
  - heroImageの行が読めない書き方の記事では移さない(使っているサムネイルを移さないため)
  - 設定で切り替える(既定は有効。`settings.json`を読めなかったときは無効で始める)。移せなくても保存は失敗にしない。移す先に同じ名前があれば上書きする
  - 保存のたびに、移した画像のうち参照されているものを元の名前で戻す(設定によらない。`assets/{slug}/`に同じ名前があれば戻さない)
  - 本文の画像を取り込むとき、移した画像に中身が同じものがあれば、新しい番号を振らずに元の名前で戻す(名前の順で最初のもの。`assets/{slug}/`に同じ名前があるものと、`hero.`で始まる名前は選ばない)
  - 画面が画像を読むとき、`assets/{slug}/`に無ければ移した先から読む(Ctrl+Zで参照を戻してから次の保存までの間も表示できるように)
  - slugを変えたら移した画像も移し、記事を作るとき・削除したときはそのslugの移した画像を消す。移す先のslugに残っていたものは、変更が後で失敗しても戻さない
  - GitHubの読み込みで記事が手元から消えても、移した画像には触らない
  - ほかの記事が`../../assets/{slug}/`の画像を参照していても、参照とはみなさない
  - 移した画像は手元から消えたものとして扱われ、次のCommitでGitHub上からも消える
- 本文とheroImageからは、`src/assets/`の直下の画像(`../../assets/{名前}`、以下「共有の画像」)も読んで表示する。Astroの公式のblogテンプレートの記事がこの形で書かれているため。アプリの操作では共有の画像を書き換えも消しもせず、slugの変更・記事の削除・zipの書き出しでも扱わない(GitHub連携でGitHubから取ってくるときだけ書く)
- Windowsで作れない名前(`<>"|?*`・制御文字・末尾の`.`と空白・`nul.png`などの予約名)の画像は、どのOSでも画像の参照として扱わない。同じリポジトリをWindowsでも編集するため

### 記事の保存と書き出し

- 記事のファイル名をslugとして使う
- slugに使える文字は英小文字・数字・ハイフン。Windowsの予約名(`con`・`nul`・`com1`など)は使えない。記事を作るときに入力し、あとから変更もできる
- 一覧の対象は記事のディレクトリの下の`{slug}.md`だけ。slugの形でない名前(Windowsの予約名を含む)のmdは、このアプリの管理外として一覧に載せない。assetsの下も同じで、対応するmdの無いディレクトリは載せない
- 出力の形は以下。Astroのプロジェクトに重ねれば、そのまま取り込める。記事のディレクトリの名前はAstroのプロジェクトによって違うので、設定で変えられる(既定は公式のテンプレートと同じ`blog`)

  ```
  ./src/content/blog/{slug}.md
  ./src/assets/{slug}/
  ```

- デスクトップでは設定で選んだ記事のディレクトリの下に書き出す。assetsはその2つ上の`assets/{slug}/`に置くので、本文からの参照は変わらない。選び間違いに気付けるよう、設定画面には画像の置き場所も出す
  - 選んでいなければ実行ファイルの親ディレクトリの`src/content/blog`。実行ファイルをAstroのプロジェクトに置けば、保存がそのままリポジトリへの書き込みになる
  - 自動保存がそのまま上の形で書き込むので、書き出しのボタンを置かない
- Androidは書き出し機能(zip)を付ける
  - 保存画面で選んだ場所へ書く。名前は`{slug}.zip`を初めに入れておく。zipの中身は上の形
- 自動保存する。間隔は仮に、2分ごとと、入力が止まってから15秒後とする
- 記事を切り替えるときとアプリを閉じるときは、保存していない変更があれば確認のダイアログを出す
  - ダイアログで「破棄」を選んだときに捨てるのは、最後の自動保存より後の変更だけ
  - Androidはアプリが閉じられるのを知る手段が無いので、ダイアログは出さず、アプリが裏へ回ったときに保存する
  - 新しい記事のダイアログと、開いている記事のslugの変更のダイアログは、開く前に保存する。保存できなければ開かない
- 上書きの前に直前の1世代をバックアップとして残す。バックアップは書き出しの形の外に置き、リポジトリに重ねたときに入り込まないようにする
  - アプリのデータ領域の`backup/{記事のディレクトリのパスのハッシュ}/{slug}.md`。Linuxは`~/.local/share/net.niigo.smeap/backup/`、Windowsは`%LOCALAPPDATA%\net.niigo.smeap\backup\`。別のプロジェクトにある同じslugの記事とは分ける
- 記事を削除すると、mdと`assets/{slug}/`、バックアップ、移した画像を消す。元には戻せないので、確認のダイアログを出す
  - 開いている記事を消したら、何も選んでいない状態にする。未保存の変更は確かめずに捨てる
- GitHubと連携しているときは、保存先と、記事の一覧・slugの変更・削除の扱いが変わる([GitHub連携](#github連携))

### フロントマター

ユーザーにフロントマターを書かせない。

- title: 左上のH1。書き換えるとそのまま反映する
- description: タイトルの下に置く
- 任意の項目はheroImageとupdatedDate。項目は[astro-blog-frontmatter.md](astro-blog-frontmatter.md)を参照
  - 設定画面の「フロントマター」の節で、項目ごとに有効・無効を切り替える。設定はアプリ全体で1つで、既定はどちらも有効
  - 無効にした項目は、編集画面の欄と警告を出さない。mdに書いてある値はそのまま残す
- pubDateは、説明の下に仕切り線で挟んだ行に置く。日付の入力欄にする。表示の形は端末の言語・地域の設定に従う
- updatedDateは、pubDateの行の右(幅が足りなければ次の行)に「更新日」の日付の入力欄で置く。値があれば右に外すボタンを置く。読み書きはpubDateと同じで、書く位置はpubDateの次
  - GitHubと連携している間は、保存したときに日付を自動で替える([日付の自動の更新](#日付の自動の更新))
- heroImageはタイトルと説明の右に画像で出し、押すと選び直す。未設定のときは「サムネイル未設定」と出す。右上のボタンで外せる(外すと画像のファイルを「使っていない画像」と同じ場所へ移す。本文が参照していれば残す)
- heroImageのファイル名は`hero.{拡張子}`にし、`src/assets/{slug}/`に置く。差し替えたら上書きする。拡張子が変わったときの前のファイルは、外したときと同じく移す
- heroImageが共有の画像のときも、選び直すと`src/assets/{slug}/hero.{拡張子}`に取り込む

### 画面

大まかな見た目は、Artifactsの試作(https://claude.ai/artifact/8bn9qixundRorooQHvkTdF)で固めた。試作のソースは[design/](design/)に置いてある。

- 画面とダイアログは次のとおり
  - 編集画面(デスクトップ・Android)
  - 記事一覧(デスクトップはサイドバー、Androidは左から引き出す)
  - 設定画面
  - 新しい記事・slugの変更のダイアログ(slugの入力)
  - 保存の確認のダイアログ
- 記事一覧はデスクトップでも折りたためるようにする(おおむねSCITLと同じ)
  - 各記事はタイトル、slug、日付を出す。一覧の上に新しい記事のボタン、下に設定への入口を置く
  - 記事の行を右クリック(Androidは長押し)すると、slugの変更、zipで書き出す(Androidだけ)、削除のメニューを出す。読めない記事は削除だけ
- 押せるボタン(主ボタンを除く)は、ホバー中・押している間に背景をグレーにする
- 編集画面はタイトル(H1)、説明、pubDateの行、本文の順に並べ、タイトルと説明の右にサムネイルを置く。本文の幅は最大720px
- 書式のボタンはリンクと画像の挿入の2つだけにする。見出しや太字などは手で打つほうが早いので置かない
  - 書式専用のツールバーは作らない
  - リンクのボタンは`[選択した文字]()`を入れ、カーソルを`()`の中に置く
- 画面の上のバーは、左から開閉ボタン、Commitのボタン、保存の状態(「保存済み (14:32)」など)、リンク・画像のボタンを置く。デスクトップでサイドバーを畳んでいる間とAndroidでは、開閉ボタンは同じ三本線のアイコンにする。デスクトップでもサイドバーを滑らせて開け閉めする
- 記事内検索(Issue #55)
  - 探すのは本文だけ。置換はしない。入力した文字をそのまま探し、正規表現・単語単位の切り替えは置かない
  - 大文字と小文字、全角と半角(NFKDで同じになるもの)は区別しない。ひらがなとカタカナは区別する。NFKDで分かれた文字の途中までの一致は外す(「カ」で「ガ」や「ｶﾞ」に当たらない)
  - デスクトップは`Ctrl+F`で、本文の領域の右上に箱を浮かせる。上のバーに検索のボタンは置かない。Androidは上のバーの右端の検索のボタンで、上のバー全体を検索の行に替える
  - 開くときに本文で1行に収まる範囲を選んでいれば、その文字で探す。そうでなければ前回の文字を残す。選択の先頭から後ろへ探し、打つたびに一致を選び直す
  - 一致にはアクセント色の下線を付ける。今の一致は選択範囲にする。件数は`2 / 5`の形で、選択が一致でなければ`5件`、一致が無ければ「該当なし」
  - 閉じると本文にフォーカスを戻し、選択は今の一致のまま残す。記事を切り替えると閉じる。ダイアログ・設定画面・メニュー・引き出した記事一覧を開いている間は`Ctrl+F`を無視する
- リンクは次の方法でも入れられる
  - 文字を選んだ状態でURLを貼り付けると`[文字](URL)`にする
  - URLだけを書いた場合はそのままにする。AstroのMarkdownはGFMが既定で有効なので、URLだけでもリンクになる。編集欄ではURLに下線を付けてリンクだと分かるようにする
- 設定画面の中身は、今のところGitHub、記事の保存先、フロントマター、画像(使っていない画像の片付け)、このアプリのライセンス、オープンソースライセンスの画面への入口
  - 設定は`settings.json`に持つ。Linuxは`~/.config/net.niigo.smeap/settings.json`、Windowsは`%LOCALAPPDATA%\net.niigo.smeap\settings.json`(Roamingにすると、端末ごとの記事の保存先がほかの端末へ同期されることがあるため)
  - オープンソースライセンスの画面は、使っているパッケージ(JS・Rustのクレート・フォント)を1件1行で並べ、押すと全文を出す。名前で絞り込める。一覧はビルドのときに作る(`scripts/licenses.ts`)。Rustのクレートが載るのは`tauri build`のときだけ
  - Windowsでは、exeに組み込まれるWebView2 SDKのWebView2Loaderも載せる。Androidでは、APKに入るJava・Kotlinのライブラリを、AndroidX・Material Components・Kotlin・Jacksonのプロジェクトごとに1件で載せる(Gradleの依存を集める仕組みは持たない)
  - ライセンスの種類ごとにはまとめない。MITなどは著作権表示がパッケージごとに違い、それも載せる必要があるため
- 新しい記事・slugの変更のダイアログでは、slugに使えない文字やWindowsの予約名が入るとその場で知らせ、書き出し先のパスも見せる
- 保存の確認のダイアログのボタンは、左から「破棄」「キャンセル」「保存」。「破棄」は左端に置き、キャンセルと保存はほかのダイアログと同じく右寄せで並べる
- ダイアログのボタンは文字もボタンの並びも折り返さない。1行に収まらなければ文言を短くする

### 見た目

基本はSCITL(`~/Documents/SCITL-2.0`)にならう。

- Markdownのレンダリングは最小限にする。記号は消さず、スタイルと画像の表示だけを付ける
- フラットデザインにする。SCITLの塗りの段差や影は使わず、文字と最低限の仕切り線で表す
- 色は白(HSV(0,0,98))と黒(HSV(0,0,0))を基本に、灰色と淡いアクセント色を使う
  - 文字の灰色は、ライト`#707070`(明度44%、白地と4.7:1)、ダーク`#8C8C8C`。明度50%だと白地と3.8:1で、小さい文字に要る4.5:1に届かないため
  - 仕切り線は、ライト`#E0E0E0`、ダーク`#262626`
- 書体

  | 箇所 | 書体 | ウェイト |
  |---|---|---|
  | 見出し・太字 | Noto Sans JP | 500 |
  | 画面の文字(ボタン・メニューなど) | Noto Sans JP | 400 |
  | 上記以外(本文など) | Noto Serif JP | 400 |

- アクセント色のシードはHSL(35,95,55)(`#F99E1F`)
  - アクセント色は、選択中の記事・カーソル・フォーカスといった状態を示す細い線と小さな印にだけ使う。文字の色にはしない。面を塗るのは、薄めた色での選択範囲だけ
  - 明暗それぞれの色は、色相を保ったまま、地の色とのコントラストが目標の値になる明度でとる
  - ライト: `#D57C00`(HSL(35,100,42))、白地と3.0:1。鮮やかさを優先したため、小さい文字に要る4.5:1には届かない
  - ダーク: `#F99D1D`、黒地と9.9:1(シードとほぼ同じ)
  - 選択範囲の淡い塗りは、ライト`#F0DFC8`、ダーク`#3E2D16`
  - 今のところ使う場所は、選択中の記事の左の印、カーソル、フォーカスの枠と、薄めた色での選択範囲の塗り。リンクは文字色を変えず下線だけ付ける。細かい調整は作りながら行う
- アイコンはGoogleのMaterial Symbols
- ダークテーマ(黒地に白)を用意し、OSの設定に合わせて切り替える

### GitHub連携

- 端末にリポジトリを持たず、GitHubのREST APIで記事のファイルを読み、コミットとブランチの作成もAPIで行う。GitHub以外には対応しない
- GitHubにログインしてRepositoryを選んでいる間は連携する。ログアウトしているか、Repositoryを選んでいなければ、今までと同じくローカルのディレクトリに読み書きする
- リモートに書くのは、Commitのボタンと、確認のダイアログを経た削除・非公開・編集の取りやめだけ。自動保存は手元にだけ書く
- PRの作成・マージ、CI・プレビューの表示は作らない。GitHubの公式アプリやWebで行う
- 編集中の記事のベースのブランチ側が変わったことは知らせない(PRをマージするときにGitHubがconflictを出す。#69で検討する)
- 画面の文言では、commit・pullは英語のまま、ブランチ・リポジトリはカタカナで書く。GitHub上に直接commitするので、pushとは書かない。remoteは使わず「GitHub上の〜」と書く

#### 認証

- SMEAP用のGitHub Appを登録し、デバイスフローで利用者の認可を得る。client IDはコードに持つ。client secretは使わない(デバイスフローで得たトークンは、secretなしで更新できる)
- Appの権限はContents(読み書き)とMetadata(読み取り)だけ。トークンが触れられるのは、Appを入れたリポジトリ(入れるときに選んだもの)のうち、利用者も触れられるものだけになる
- Appの設定でトークンの期限切れを有効にしておく(既定)。トークンは8時間、更新用のトークンは6か月で切れる。期限が切れていたら更新用のトークンで取り直し、取り直せなければもう一度ログインさせる。更新のたびに更新用のトークンも替わるので、新しい組を書き終えてから古い組を捨てる
- トークンは画面には渡さない。ログ・エラー文にも出さない
  - デスクトップでは、OSの資格情報の保存先(Windowsは資格情報マネージャー、LinuxはSecret Service)に、サービス名`net.niigo.smeap`・ユーザー名`github`の項目で置く。使えなければログインできない(ファイルには置かない)
  - 前の版がデータ領域に作った`github/token.json`は、起動時に資格情報の保存先へ移して消す
  - Androidはアプリのデータ領域の`github/token.json`に置き、OSのバックアップの対象から外す(マニフェストの`dataExtractionRules`・`fullBackupContent`)
- 通信はRust側で`ureq`(rustls、ルート証明書は同梱)で行う
  - 宛先は`https://api.github.com/`と、`https://github.com/login/device/code`・`https://github.com/login/oauth/access_token`に限り、それ以外のURLは組み立てた時点で弾く。リダイレクトは追わない
  - `User-Agent`と`X-GitHub-Api-Version`を付ける
  - レート制限(403・429)は自動で再試行せず、いつ再開できるかを出して止める
- ブラウザを開くのは、認可のページ(`https://github.com/login/device`)とAppのインストールのページだけ。開くのはRust側で、URLは固定

#### 設定

設定画面の「GitHub」の節に、上から次の順で並べる。ログインしていなければ「GitHubにログイン」のボタンだけを出し、リポジトリを選ぶまではベースブランチ以下を出さない。

| 項目 | 既定 | 備考 |
|---|---|---|
| アカウント | | ログインしている名前と、ログアウト |
| リポジトリ | なし | トークンで触れられるrepositoryの一覧から選ぶ |
| ベースブランチ | default branch | |
| ブランチ名の形式 | `blog/{slug}` | `{slug}`をちょうど1つ含む |
| 記事ディレクトリ | `src/content/blog` | repositoryの中のパス。画像は今と同じく、その2つ上の`assets/{slug}/` |

- 並びは、branch→その中のディレクトリという実際の階層に合わせる
- branch名の形式は、`{slug}`にslugを入れた名前がGitのブランチ名の決まり(`git check-ref-format`)に合うかで確かめる
- 記事のディレクトリは`/`区切りの相対パスに限る。空の部分・`.`・`..`・`\`・`.git`を含むものは受け付けない。2つ上が無い(深さ2未満の)ものも受け付けない
- 連携している間は「記事の保存先」の節を隠す
- ログイン・ログアウトやRepositoryの切り替えのときは、開いている記事を保存してから閉じ、保存層の向き先を替える(Androidにも`set_posts_dir`を使えるようにする)。それぞれの手元の記事はそのまま残り、移し替えはしない。ログアウトはトークンを消すだけ
- 設定は1つの`settings.json`に足す。1項目を変えるときに、ほかの項目を消さないよう読み直してから書く

#### 手元の記事

- アプリのデータ領域の`github/{owner}/{repo}/files/`の下に、リポジトリと同じ並び(`src/content/blog/{slug}.md`、`src/assets/{slug}/`)で記事のファイルだけを置く。読み書きは今の保存層がそのまま行う
- 記事ごとに、手元の内容がどのリモートの内容から来たかを`github/{owner}/{repo}/state.json`に持つ
  - 元にしたブランチ(ベースか記事用か)とコミット
  - 元にしたときの記事のファイルの一覧(mdと`assets/{slug}/`の下)と、それぞれのblobのSHA(`blob {バイト数}\0{内容}`のSHA-1)、手元に取ってきたか
- 元にしたときのmdの中身も`github/{owner}/{repo}/synced/`に写しておく(Commitのダイアログで差分の行数を出すため)
- 手元のファイルのSHAを記録と比べ、違うもの・増えたもの・(取ってきたのに)消えたものがあれば「commitしていない変更がある」とみなす。まだ取ってきていない画像が手元に無いのは変更ではない
- 新しく作ってまだ一度もcommitしていない記事は、記録が無く、全体が変更として扱われる
- `state.json`に版番号を持たせる。読めないときは空として続けず、読み込みとCommitを止めて知らせる。一覧は分類せずに出す
- `state.json`には、ベースのブランチ・branch名の形式・記事のディレクトリの設定も持たせ、今の設定と違えば記録が無いものとして扱う。中身がリモートと同じ記事は、次の読み込みで記録が直る
- `assets/{slug}/`の下のディレクトリにあるファイルは、記録はするが取ってこない(保存層も編集欄も、画像は`assets/{slug}/`の直下のファイルだけを扱うため)
- Windowsで作れない名前の画像と、GitHub上の同じディレクトリにあるほかの画像と大文字小文字だけが違う名前の画像(`A.png`と`a.png`)も、記録はするが取ってこない。共有の画像も同じく取ってこない。Windowsでは後者が1つのファイルになり、上書きし合うため
- 共有の画像は記事のファイルに含めない。記録に入れず、commitしていない変更の判定・Commit・Conflict・Pull・slugの変更・削除・編集の取りやめのどれでも扱わない
- 自動保存と保存の確認は今のまま

#### 日付の自動の更新

- 保存のときに、Rust側で記事の分類を見て日付を今日(端末の時刻での日付)にする
  - 公開済みの記事(ベースのブランチにある記事と、公開済みの記事からslugを変えた記事)はupdatedDate。設定でupdatedDateを無効にしていれば替えない
  - それ以外はpubDate
- 日付を除いた内容(title・description・本文)が保存されているmdと同じなら替えない。入力して元に戻しただけの保存で、公開済みの記事が編集中にならないように
- ベースのブランチの様子がまだ無いときと、`state.json`が読めないときは、分類が分からないので替えない
- 手で直した日付(外したことを含む)には記事ごとに印を付け、印のある日付は自動で替えない
  - 保存の結果として書いた日付を返し、画面は保存を頼んでから返るまでに手で変えていない日付の欄をその値にする
  - pubDateの印は、公開済みの記事を保存したときに外す。updatedDateの印は、Commitが成功したとき(送っている間に手元のmdが変わっていなければ)と、Pull・編集の取りやめで外す
  - 記事を作るときと、まだ公開していない記事を削除したときに外し、slugを変えたら付け替える
- 印は`github/{owner}/{repo}/dates.json`に持つ(まだcommitしていない記事にも要るので、`state.json`とは分ける)。ほかの端末には伝わらない
  - 印はmdより先に書く。書けなければ保存を失敗にする。slugの変更も、印を移せなければ断る
  - 読めなければ、日付を自動で替えず、印も書かずに保存する
- mdの日付の行が読めない書き方なら、その行を残すために自動で替えない

#### 一覧

サイドバーを3つに分ける。

| 分類 | 条件 |
|---|---|
| 執筆中 | ベースのブランチに無い記事。記事用のブランチにあるものと、まだcommitしていないもの |
| 編集中 | ベースのブランチにあり、記事用のブランチがあるか、手元に変更がある記事 |
| 公開済み | ベースのブランチにあり、上のどちらでもない記事 |

- 記事用のブランチの記事の内容(ファイルの一覧とSHA)がベースのブランチと同じなら、マージ済みとして公開済みに入れる。squash mergeでもそうなるよう、コミットではなくファイルで比べる
- 分類ごとに見出しと件数を出す。件数が0の分類は見出しも出さない。一覧の上には、repository名と最後に読み込んだ時刻(読み込めなかったときはそのこと)を出す。読み込めなかったときは、押すと理由を出す
- 行には、commitしていない変更の印(アクセント色の小さな丸)と、GitHub上の内容と食い違っている印(`sync_problem`のアイコン、エラーの色)を出す
- 開くときにブランチの切り替えは要らない。記事ごとにどのブランチから来たかを覚えていて、Commitのときにそれを使う
- 記事用のブランチにその記事が無くても、リモートの様子に入れる(空のブランチ)。ベースにその記事があれば削除予定の記事になり(下の「公開済みの記事の削除・非公開」)、無ければ記事としては扱わない(下の「空のブランチ」)
- 削除予定の記事は編集中に入れ、行に`delete`のアイコン(非公開にした記事は`visibility_off`)を出す
- ほかの記事を移した記事用のブランチ(下の「公開済みの記事のslugの変更」)の記事と、`renamedFrom`の元のslugがベースにある記事は、ベースに無くても編集中に入れる。移された元の記事は、手元に変更が無ければ一覧に出さない
- 形式に合わないブランチは見ない(結び付けて開く機能は#67で検討する)。記事用のブランチに別の記事の変更が入っていても、その記事のmdと`assets/{slug}/`以外には触らない。ツリーの中で通常のファイルでないもの(サブモジュール・シンボリックリンクなど)がその記事の場所にあれば、その記事は読み込まず、一覧の下に件数を出す

#### リモートの読み込み

- 起動時と、一覧の上の更新ボタン(`sync`)を押したときに読み込む。読み込む前に、開いている記事に未保存の変更があれば保存する
- 読むのは、ベースのブランチと、branch名の形式の`{slug}`より前の部分で始まるブランチの一覧(`/git/matching-refs`、ページを最後までたどる)と、それぞれの記事のディレクトリ・`assets/`の下のツリーだけ。一覧のうち、形式の`{slug}`より後ろの部分で終わり、間がslugとして正しいものだけを記事用のブランチとして扱う。リポジトリ全体の再帰ツリーは取らない。ツリーが切り詰められていたら(`truncated`)、その記事のディレクトリまで下りて取り直す
- mdは、SHAが記録と違うものだけを取ってくる。画像は、まだ取ってきていないものを記事を開く前に取ってくる。取ってこられなくても記事は開き、画像は表示できないままにして、取れなかったことを出す
- 共有の画像は、ベースのブランチの`assets/`の直下の通常のファイルの名前とSHAを`state.json`のリモートの様子に持ち、記事を開く前に、手元のmdが参照しているもののうち手元に無いかSHAが違うものを取ってくる
  - 手元の共有の画像は記事のあいだで1つなので、記事用のブランチで変わっていてもベースの内容に合わせる
  - 前のバージョンが書いた`state.json`にはこの一覧が無いので、ベースのブランチの先頭が前回と同じでもツリーを取り直す
- ブランチの先頭のコミットが前回と同じなら、ツリーは取り直さない
- どこかで失敗したら、その回の読み込みでは手元も`state.json`も書き換えない。手元を書き換える途中で落ちたときのために、書き換える前に`state.json`に新しい記録を途中の記録として書いておき、次の読み込みでは、手元のファイルがどれも古い記録か途中の記録のどちらかと同じなら変更が無いものとして扱う
- 読み込みの間にログイン・ログアウト・Repositoryや設定の変更があれば、その回の結果は書かない
- 読み込めない記事(上の「一覧」)は、その回は手元も記録も替えず、次の読み込みでも調べ直す
- 開いている記事は、編集欄に保存していない入力があるかをRust側で知れないので、読み込みでは置き換えも削除もしない。そうなるはずだったときは、入力が無ければ、編集欄に入力させないようにしてからもう一度読み込んで置き換え、入力があれば保存してから読み込み直す(手元の変更として扱われる)。読み込みの間は、ほかの記事への切り替えと自動保存も止める
- 記事ごとの扱い

| リモートの様子 | 手元に変更が無い | 手元に変更がある |
|---|---|---|
| 記録と同じ | そのまま(記録のコミットだけ先頭に合わせる) | そのまま(同左) |
| 変わった | リモートの内容に置き換える | 置き換えず、食い違いの印を付ける |
| ベースのブランチから記事が消えた(記事用のブランチは無い) | 手元からも消す | 執筆中のまだcommitしていない記事として残す |
| 記録していた記事用のブランチが消えた | ベースのブランチにあればその内容に戻し、無ければまだcommitしていない記事として残す | ベースのブランチにあれば、手元は替えずに記録をその内容にする(編集中になる)。無ければまだcommitしていない記事として残す |

- 手元の内容がリモートと同じなら、記録が古くても、リモートに合わせて記録を直す(コミットした直後に落ちた場合など)
- 記事用のブランチが消えて手元に変更があり、ベースのブランチにあるときに記録をベースの内容にするのは、Commitのダイアログで差分の行数をベースとの差にし、Commit messageの初期値を「{title}を修正」にし、GitHub上での変更との食い違いを調べられるようにするため
- 元にしたブランチが替わった(ベースの記事に記事用のブランチができたなど)ときも「変わった」として扱う
- 記事のある記事用のブランチのうち、slugがベースに無いものは、`GET /compare/{ベースの先頭}...{ブランチの先頭}`で、ベースとの分岐点から消した・名前を変えた(`removed`と、`renamed`の`previous_filename`)記事のmdを調べる。記事のディレクトリの直下のmdで、slugとして正しく、ベースにあるものを、そのブランチが移した記事としてリモートの様子に持つ。ブランチの先頭が前回と同じなら調べ直さないが、移した記事が今のベースで成り立つか(元のslugがベースにあり、そのブランチのslugがベースに無いか)は毎回確かめ、成り立たなければ外す
  - ブランチのツリーだけで比べないのは、ベースに記事が増える前に切ったブランチにも、その記事が無いため
  - `files`は300件までしか返らず、続きを取る方法が無い。300件あれば、そのブランチの記事を読めない記事にする
  - 移した記事が2つ以上あるときと、共通の祖先が無い(404)ときも、読めない記事にする。それ以外の失敗は読み込みを止める
- 移された元の記事は手元に作らない。手元にあれば、変更が無ければ手元から消し、変更があれば残して食い違いの印を付ける
- `renamedFrom`のある記事は、手元に変更があるものとして扱う。記録のブランチが無ければ、リモートの内容はベースの元のslugの記事にする。ベースから消えていれば、記録を消し、まだcommitしていない記事として残す
- 削除予定の記事のリモートの内容は、空のブランチとその先頭のコミットに、ベースの記事のファイルを合わせたものにする。記録には削除予定の印(削除か非公開か)を持つ。扱いは次の表のとおりで、それ以外は上の表と同じ

| リモートの様子 | 手元に変更が無い | 手元に変更がある |
|---|---|---|
| 削除予定になった(記録に印が無い。ほかの端末で削除した) | 記録を削除予定にする(印は削除) | 食い違いの印を付ける |
| 削除予定のまま、ベースの記事が変わった | ベースの内容に置き換える | 食い違いの印を付ける |
| ベースから記事が消えた(マージした。ブランチも消えたときを含む) | 削除なら手元から消す。非公開なら記録を消し、まだcommitしていない記事として残す | 記録を消し、まだcommitしていない記事として残す |
| 空のブランチが消えた | ベースの内容に戻り、印を外す | 記録をベースの内容にし、印を外す(編集中になる) |
| 空のブランチに記事が足された | 印を外し、「変わった」と同じに扱う | 同左 |

- 削除か非公開かは手元の記録にだけ持つ。ほかの端末では削除として扱う
- 空のブランチが無ければ、扱いによらず記録の印を外す
- 手元に変更が無い記事を置き換え・削除してよいのは、その内容がリモートのGitの履歴に残っているため。記事用のブランチが消えたときは、その内容がどこにも残っていないことがあるので、手元から消さない

#### Commit

- 1回の操作でコミットを作ってブランチを進めるので、画面ではGitのcommitとpushをまとめた操作として見せる
- 上のバーの、開閉ボタンのすぐ右に、Commitのボタン(`upload`のアイコンだけ)を置く。commitしていない変更があればアイコンにアクセント色の小さな丸を重ね、無ければ灰色にして押せなくする。連携していないときは出さない
- ボタンを押すと、Commitのダイアログを出す。送り先のブランチは出さない(記事ごとに決まっているため)
  - 本文の行: mdのファイル名と、元にしたときのmdとの行単位の差分(`+12 −3`)。初めてのcommitは全行が`+`
  - 画像の行: 追加・削除の件数(`追加 1件 / 削除 1件`)。画像の変更が無ければ出さない。差し替えは削除と追加に数える
  - slugを変えた後は、本文の行を`古い名前.md → 新しい名前.md`にし、古いブランチを消すことを1行で出す
  - Commit messageの入力欄。初期値は、初めてのcommitなら「{title}を追加」(編集中の記事は「{title}を修正」)、2回目以降は「{title}を更新」。空白だけなら送れない
- 押す前に未保存の変更があれば、先に保存する
- 手順
  1. 記事用のブランチがあれば記録したコミット、無ければベースのブランチの先頭を親にする
  2. 記録と比べて変わった・増えたファイルをblobにし、消えたファイルを外して、親のツリーに重ねたツリーを作る。`assets/{slug}/`の下は手元にあるものをそのまま送る(本文から参照されていない画像も)
  3. コミットを作り、ブランチを作る(`POST /git/refs`)か進める(`PATCH /git/refs`、`force: false`)
- `force: false`は早送りかどうかしか確かめないが、新しいコミットの親は記録したコミットなので、リモートがその後に進んでいれば早送りにならず失敗する
- 記事用のブランチが無くベースのブランチの先頭を親にするときも、その先頭の記事のファイルを記録と比べ、下の「進められなかったとき」と同じに扱う。`POST /git/refs`はベースが進んだことでは失敗しないため
- ブランチを進められなかったときは、リモートの先頭を読み直し、記録と比べてリモートで変わったファイルを調べる。作り直しは3回までにする
  - 手元で変えたファイルとリモートで変わったファイルが重ならなければ、ダイアログを出さずに、リモートの先頭を親にして手順2から作り直す(リモートの変更はそのまま残る)
  - 重なっていれば、題「競合(Conflict)」、本文「「{title}」の本文がGitHub上でも変更されています。」(画像なら「画像 {名前} が」)のダイアログを出す
    - 本文が重なっていれば本文の文言だけを出す。そうでなければ、重なった画像の名前を「、」でつなぐ
    - 「Commit」: ダイアログを出したときのリモートの先頭を親にして作り直す。重なったファイルは手元の内容になる(履歴は書き換えないので、force pushとは呼ばない)。その後にさらに進んで重なっていれば、もう一度このダイアログを出す
    - 「Pull」: 手元の記事のファイルを`github/{owner}/{repo}/backup/{日時}/`に`files/`と同じ並びで写してから、リモートの内容で置き換える。日時は端末の時刻で`YYYYMMDD-HHMMSS`、同じ名前があれば`-2`、`-3`…を付ける
    - 「キャンセル」
- 記事用のブランチを作ろうとして、同じ名前のブランチが既にあったとき(ほかの端末で同じslugで書き始めたなど)は、題「ブランチが既に存在します」、本文「{名前} は既に存在しています」のダイアログを出す。ボタンは「Pull」(手元はバックアップに写す)と「キャンセル」
- 記録していた記事用のブランチがGitHub上で消えていたときは、何も作らずに読み込み直し、「GitHub上のブランチが削除されていたため、再読み込みしました」を出す。読み込みで記録がベースの内容に戻るので、もう一度押せばブランチを作り直す
- 送っている間は、押せないPullとキャンセルのボタンを外し、そこに回るアイコンと今の段階を出す。文言は短くし、段階が替わっても主ボタンの大きさと位置は変えない。段階は次の順に進み、作り直すとき(「進められなかったとき」)は「確認中」に戻る
  1. 「確認中」: ボタンを押したときから。トークンの更新、ブランチの先頭と親のコミットの記事の読み込みを含む
  2. 「送信中 ({n}/{m})」: blobを送る。mは送るファイルの数(中身が同じファイルは1つに数え、作り直しで送り済みのものは数えない)、nは今送っているものの番号。送るものが無ければこの段階は出さない
  3. 「Commit中」: ツリーとコミットを作る
  4. 「ブランチを更新中」: ブランチを作るか進める。slugを変えた後は、新しいブランチを作ってから古いブランチを消し終えるまで
- Conflictのダイアログの「Commit」でも同じに出す。「Pull」と、送り終えた後の読み込み直しでは出さない(ボタンを押せなくするだけ)
- 失敗したら段階の行を消し、エラーを出す
- 成功したら、上のバーに「Commitしました」を出し、GitHubから読み込み直す
- 作り直しでリモートの変更を取り込んだときと、Pullのときは、手元のファイルを直接書き換えず、記録を手元の内容にして書く。次の読み込みで「手元に変更が無く、リモートが変わった」記事として、リモートの内容に置き換わる

#### slugの変更・削除

連携している間は、記事の行のメニューを分類で替える。

| 分類 | メニュー |
|---|---|
| 執筆中 | slugを変更、削除 |
| 編集中 | slugを変更、編集をやめる |
| 編集中(削除予定) | 削除をやめる(非公開にした記事は「非公開をやめる」) |
| 公開済み | slugを変更、非公開にする、削除 |

- Androidのzipでの書き出しは、連携している間は出さない
- 編集中の記事の削除・非公開は出さない。先に編集をやめてもらう(送ったcommitの内容と手元に残す内容を揃えるため)
- 分類はRust側でも確かめる。削除予定の記事のslugの変更と、公開済みでない記事の非公開、編集中の記事の削除は断り、「公開済みの記事のみ可能な操作です」を出す
- `state.json`が読めないときは、新しい記事・slugの変更・削除・非公開・編集の取りやめを断る
- 新しい記事・slugの変更・削除・非公開・編集の取りやめは、読み込み・Commit・Pullと同時には行わない(動いていれば断り、「GitHubと同期中です」を出す)

##### slugの変更

- まだcommitしていない記事(記録が無い)は、今までと同じく手元だけで変える。ただし、記録が無くても前回読み込んだリモートの様子に記事用のブランチがある記事(手元と食い違っている)は、「GitHub上の内容と競合しています」を出して断る
- 削除と編集の取りやめで消す記事用のブランチも、記録に無ければ前回読み込んだリモートの様子から選ぶ
- 記事用のブランチのある記事は、手元のファイルとsyncedを移し、記録を新しいslugに付け替えて、元のslugを記録に持つ(`renamedFrom`)。続けて変えても、元のslugは最初のものを持ち続ける。元のslugに戻したら外す
- `renamedFrom`のある記事は、中身が記録と同じでも、commitしていない変更があるものとして扱う
- 次のCommitで、新しい名前のブランチを作る
  1. 記録のブランチ(古いブランチ)の先頭を読む。消えていれば今と同じくBranchGoneにする
  2. 先頭が記録のコミットと違えば、記事用のブランチが無いときのベースの先頭と同じく、先頭の記事のファイルを記録と比べて重なりを調べる(Conflictのダイアログも同じ)
  3. その先頭を親にし、古いパスのファイル(mdと`assets/{古いslug}/`の下すべて)を外し、新しいパスに足したツリーでコミットを作る。手元に取ってきていない画像と下のディレクトリのファイルは、親のblobのSHAをそのまま使う
  4. 新しいブランチを作る(`POST /git/refs`)。同じ名前のブランチが既にあれば、今の「ブランチが既に存在します」のダイアログにする。Pullを選ぶと`renamedFrom`を外して新しいブランチの内容に読み込み直し、古いブランチは残す(次の読み込みで古いslugの記事として出る)
  5. 記録を新しいブランチに替えて`renamedFrom`を外し、その後で古いブランチを消す。消す前に先頭が親にしたコミットと同じか確かめ、違うか消せなければ残して、「Commitしましたが、{名前}の削除に失敗しました」を出す(次の読み込みで古いslugの記事として出る)
- Commitのダイアログは、本文の行を`古い名前.md → 新しい名前.md`にし、その下に「ブランチ {古い名前} は削除されます。」を出す。Commit messageの初期値は「{title}を更新」
- リモートの読み込みでは
  - `renamedFrom`のある記事のリモートの内容は、記録のブランチにある元のslugの記事にする。ベースは見ない。ブランチが消えていれば記録を消し、まだcommitしていない記事として残す(今の「記録していた記事用のブランチが消えた」でベースに無い場合と同じ)。次のCommitはベースの先頭を親に新しいブランチを作る
  - それ以外は今の表と同じに扱い、「手元に変更があるか」は中身だけで決める。置き換えても`renamedFrom`は残す
  - 元のslugの記事は、記録のブランチにあってもベースにあっても読み込まない(手元に作り直さない)
- 元のslugは、Commitで外れるまで、新しい記事とslugの変更の行き先に使えない。「変更前のslugは、Commitが完了するまで再使用できません」を出す
- 行き先のslugが、前回読み込んだリモートの様子(ベースの記事・記事用のブランチ・読めない記事)にあれば断る。「GitHub上に同じslugの記事が存在します」を出す
- 4の後で記録を書けなかったときは、次のCommitで新しいブランチが既にあることになり、「ブランチが既に存在します」のダイアログからPullで直す

##### 削除

- 確認のダイアログは今のもの(題「記事を削除する」、ボタン「削除する」)を使い、記事用のブランチがあれば「GitHub上のブランチも削除されます。」の1行を足す。`renamedFrom`のある記事は古いブランチを消す
- 記事用のブランチがあれば、その先頭が記録したコミットと同じか確かめてからブランチを消し、手元のファイル・synced・記録を消す
  - 先頭が違えば何も消さず、「GitHub上のブランチが更新されています」を出す
  - ブランチが既に無ければ、手元だけ消す
  - GitHubのブランチの削除には先頭を指定する条件が無いので、確かめてから消すまでの間にほかの端末が進めたコミットは失われ得る(間は1回の通信だけ)
  - ブランチを消した後に手元を消せなければ、次の読み込みで記録が消え、まだcommitしていない記事として残る
- まだcommitしていない記事は、今までと同じく手元だけ消す

##### 編集をやめる

- 題とボタンは「編集をやめる」、本文は「「{title}」({slug})の変更を破棄し、公開済みの内容に戻します。」。記事用のブランチがあれば「GitHub上のブランチも削除されます。」の1行を足す
- 手順
  1. ベースのブランチの先頭と、そこでの記事を読む。記事が無ければ何もせずArticleNotFoundにする
  2. 記事用のブランチがあれば、削除と同じく先頭を確かめてから消す
  3. 手元をベースの内容にする。mdはベースの内容で書き換え、画像はSHAが同じものだけ残す(読み込みの置き換えと同じ)。記録をベースの内容にし、syncedを書き直し、食い違いの印を外す
- ブランチを消した後に手元を書き換えられなければ、次の読み込みで記録がベースの内容になり、編集中の記事として残る(もう一度やめられる)
- 開いている記事なら、確定したときに編集欄を入力できなくし、自動保存を止める。未保存の入力は捨て、終わった後に開き直す。失敗したら編集欄を戻す
- 削除・編集の取りやめに失敗したら、ダイアログに理由を出す(通信の失敗などは今のGitHubの文言を使う)

##### 公開済みの記事の削除・非公開

- 確認のダイアログ
  - 削除: 題「記事を削除する」、本文「「{title}」({slug})を削除するブランチ {branch} を作成します。この記事は {branch} のマージ後に削除されます。」、ボタン「削除する」
  - 非公開: 題・ボタン「非公開にする」、本文「「{title}」({slug})を削除するブランチ {branch} を作成します。この記事は {branch} のマージ後も執筆中の記事として残ります。」
- 開いている記事なら、確定したときに保存してから編集欄を入力できなくし、自動保存を止める。失敗したら編集欄を戻す
- 手順
  1. ベースのブランチの先頭と、そこでの記事のファイルを読む。記事が無ければArticleNotFound。手元の記事が記録と違うか、記録がベースの記事と違えば、「GitHub上の内容と食い違っています」で断る
  2. 親を決める。記事用のブランチ(マージした後に残ったもの)があれば、その先頭が記録したコミットと同じで、そこでの記事のファイルがベースと同じか確かめて親にする。違えば「GitHub上のブランチが更新されています」。無ければベースの先頭を親にする
  3. 記録に削除予定の印(削除か非公開か)を付けて書く
  4. 親に、記事のmdと`assets/{slug}/`の下のファイル(下のディレクトリも含む)を外したツリーでコミットを作る。Commit messageは「{title}を削除」「{title}を非公開に」(titleが空ならslug)
  5. 記事用のブランチを進める(`PATCH`、`force: false`)か作る(`POST`)。失敗したら先頭を読み直し、作ったコミットになっていれば成功にする。進めるときに親から進んでいれば2の「更新されています」、作るときに422でブランチがあれば「{branch} は既に存在しています」、それ以外は元のエラー。作り直しはしない
  6. 記録を、ブランチとそのコミット、ベースの記事のファイルにし、リモートの様子のブランチも空のブランチとして書く。手元のファイルは替えない
- 失敗したら、3の印を外す。ただし、5の通信が切れたときと、5の後に先頭を読み直せなかったときは、ブランチを書き換えたか分からないので印を残す(次の読み込みで、届いていなければ外れ、届いていれば残る)。6の記録を書けなかったときは成功にする(印があるので、次の読み込みで記録が削除予定になる)。画面は失敗の後にも一覧を読み直す
- 送っている間は、ダイアログの主ボタンを押せなくし、Commitと同じく段階(「確認中」「Commit中」「ブランチを更新中」)を出す
- 削除予定の記事は、開くと編集欄を入力できなくし(上のバーの挿入と、画像のドロップも止める)、上のバーに「削除予定」(非公開なら「非公開予定」)と出す。Commitのボタンは押せない(Rust側でもNothingToCommitで断る)
- 削除・非公開をやめるのは、「編集をやめる」と同じ手順(ブランチの先頭を確かめてから消し、ベースの内容に戻して印を外す)。題とボタンは「削除をやめる」「非公開をやめる」、本文は「「{title}」({slug})を公開済みの内容に戻します。」と「GitHub上のブランチも削除されます。」

##### 空のブランチ

- ベースにも記事が無い空のブランチは、新しい記事と執筆中の記事のslugの変更の行き先のslugにしてよい
- まだcommitしていない記事のCommitで、送り先の名前の空のブランチが前回読み込んだ様子にあれば、作らずにその先頭を親にして進める(`PATCH`、`force: false`)。先頭を読み直して記事が足されていれば「ブランチが既に存在します」にする
- 削除のPRをマージした後にブランチが残っているとき(GitHubの既定ではマージしてもブランチは消えない)に、非公開にした記事や同じslugの新しい記事を送れるようにするため

##### 公開済みの記事のslugの変更

- slugの変更のダイアログに、公開済み・編集中の記事なら「公開済み記事のURLが変更されます」の1行を足す
- 手元では、記事用のブランチのある記事と同じく、手元のファイルとsyncedを移し、記録を新しいslugに付け替えて`renamedFrom`を持つ。記録のブランチが無い(ベースの)記事でも記録を残す
- この記事の元のslug(`renamedFrom`か、記録のブランチが移した記事)へ戻すのは、ベースにあるslugでも許す
- 空のブランチのslugへは移せない(下の3で進められないため)。「GitHub上に同じslugの記事が存在します」を出す
- 記録のブランチが無い記事の次のCommit
  1. ベースのブランチの先頭を読み、そこでの元のslugの記事を記録と比べて重なりを調べる(Conflictのダイアログも同じ)。元のslugの記事がベースから消えていれば、何も作らずに読み込み直す(BranchGoneと同じ文言)
  2. その先頭を親に、古いパスのファイルを外して新しいパスに足したツリーでコミットを作る(手元に取ってきていない画像は親のblobのSHAを使う)
  3. 新しいブランチを作る。同じ名前のブランチが既にあれば「ブランチが既に存在します」(空のブランチでも進めない。親が元の記事を含まないことがあるため)
  4. 記録を新しいブランチに替えて`renamedFrom`を外し、同じ書き込みでリモートの様子のブランチに移した記事を書く。消す古いブランチは無い
- Commitのダイアログは、本文の行を`古い名前.md → 新しい名前.md`にし、古いブランチの行は出さない
- 移した記事(`renamedFrom`のある記事と、移した記事用のブランチの記事)の編集をやめると、記事用のブランチがあれば先頭を確かめてから消し、元のslugの記事をベースの内容で手元に作ってから、新しいslugの手元のファイル・synced・記録を消す。元のslugの記事が手元に変更つきで残っていれば(移された元の記事の食い違い)、上書きせずに「GitHub上の内容と食い違っています」で断る。本文は「「{title}」({slug})の変更を破棄し、公開済みの内容({元のslug})に戻します。」
- 移した記事のslugを続けて変えるときは、記事用のブランチのある記事と同じ(新しいブランチを作り、古いブランチを消す)。新しいブランチも同じ元の記事を移した記事として様子に書く

ブランチを消した・作ったときは、`state.json`のリモートの様子からも消す・足す(次の読み込みまでの分類を合わせるため)。足す項目(空のブランチ、移した記事、削除予定の印)は省略できるものにし、`state.json`の版は上げない。

#### ログイン・リポジトリの選択

- 設定画面の「GitHubにログイン」を押すと、ログインのダイアログを出す
  - 8文字のコードと、コードのコピー(コピーしたら2秒だけアイコンをチェックにする)、`github.com/login/device`を開くボタン、キャンセル
  - 認可されるまで、Rust側が指定された間隔で問い合わせる(`slow_down`なら間隔を延ばす)。コードの期限が切れたらそのことを出し、やり直せるようにする
- ログインした後、リポジトリの選択のダイアログを出す。一覧には、SMEAPのGitHub Appを入れたrepositoryだけが出る(Appを入れるときに、全部か選んだものだけかを決める)。一覧の下の説明は置かず、Appのインストールのページを開くボタンを「追加」の名前で置く(インストールのページでrepositoryを選び足せるため)。一覧が空なら「選択可能なリポジトリはありません」とだけ出す
